\chapter{1. Integración y demostración
preparada}\label{ACD5-semana-5-1-integraciuxf3n-y-demostraciuxf3n-preparada}

El backend real es monolito modular Spring, cliente Angular y PostgreSQL
principal. Acceso/catálogo/preparación siguen las referencias AA2, C4 y
contrato APE3. Se dispone de código y evidencia previa de 23 tests/22
intercambios en Spring/SQLite; no se presentan como nueva demostración
de Semana5. DRF/sobre universal y controles de seguridad pendientes
condicionan la aceptación del incremento.

Guion para demostrar en un entorno autorizado: identificar
versión/artefacto; iniciar fixture y verificar esquema; autenticar
usuario sintético; crear unidad/carrera, consultar/editar con ETag;
probar rechazo de duplicado/revisión vieja/CSRF/ámbito; preparar proceso
con referencias válidas; cerrar sesión y comprobar rechazo. Registrar
estados, cuerpos/headers redactados y persistencia. Health200 o Swagger
disponible no sustituyen este flujo. No se realizó esa presentación al
docente.

Los \href{../soporte-semanas-4-5/HALLAZGOS_Y_TRAZABILIDAD.md}{resultados
y trazabilidad} separan antecedentes y verificaciones pendientes. La
\href{../APE5-semana-5/INSTRUCCIONES_DESPLIEGUE.md}{propuesta de
despliegue} incluye Dockerfile/Compose locales, no una URL pública ni
contenedor ejecutado. Docker/Podman ausentes y sandbox no acreditado
impiden afirmar ejecución.

\section{Prerrequisitos y
límites}\label{ACD5-semana-5-anexo0-prerrequisitos-y-luxedmites}

Resolver la tecnología y el contrato pendientes de APE3. Si se acepta
Spring, preparar JDK/Maven y dependencias ya disponibles y verificar el
código en sandbox conforme; no usar el JAR antiguo de target sin
reconstruir y registrar hash/commit. Confirmar motor Linux de
contenedores, versiones y recursos. Las imágenes Java 25 JRE y
PostgreSQL 18 deben estar auditadas, fijadas por digest y disponibles
localmente; no se descargaron aquí. El Dockerfile espera una imagen
Linux con java, mkdir y chown: verificar esa interfaz, no asumir
compatibilidad de una distroless arbitraria.

La red Compose interna y los límites son controles de operación
propuestos, \textbf{no prueba suficiente de la sandbox de auditoría}. No
montar Docker socket, repositorio completo, home o credenciales del
host. El contexto de construcción contiene solo app.jar mediante
allowlist; \path|.env| queda fuera y está ignorado. No imprimir
\path|docker compose config| con secretos interpolados ni adjuntar
\path|docker inspect| sin redacción.

\section{Preparación reproducible
prevista}\label{ACD5-semana-5-anexo0-preparaciuxf3n-reproducible-prevista}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  En el entorno de construcción aislado, ejecutar Maven verify/package
  del commit seleccionado y conservar resultados y SHA-256 del JAR.
  Comprobar que sus dependencias/Java corresponden al POM y contrato;
  esta entrega no ejecuta ese paso.
\item
  Copiar \textbf{solo} el JAR nuevo a \path|despliegue/context/app.jar|.
  No versionarlo. Comparar hash con el artefacto verificado antes de
  construir.
\item
  Crear \path|despliegue/.env| local desde \path|.env.example|;
  proporcionar imágenes por digest, contraseña sintética de DB y secreto
  HMAC nuevo de alta entropía. No usar cadenas de ejemplo ni publicar
  valores. El archivo de ejemplo no contiene claves reales.
\item
  Revisar Compose y validar sin revelar valores. En la máquina
  autorizada, desde \path|despliegue|, la forma prevista es:
\end{enumerate}

\begin{Verbatim}[breaklines=true,breakanywhere=true,fontsize=\footnotesize]
docker compose config --quiet
docker compose build --pull=false api
docker compose up -d --no-build
docker compose ps
\end{Verbatim}

Son instrucciones \textbf{no ejecutadas}. Requieren validación semántica
con la versión instalada y las imágenes elegidas. El contexto
restringido evita enviar código/.git/secretos innecesarios al builder.
La política pull never y build pull=false no reemplaza aislar el builder
de red externa.

\section{Persistencia, arranque y
seguridad}\label{ACD5-semana-5-anexo0-persistencia-arranque-y-seguridad}

PostgreSQL 18 oficial usa almacenamiento bajo
\path|/var/lib/postgresql|, diferente de convenciones de versiones
previas: el volumen se fija ahí y debe contrastarse con la
imagen/digest. Nunca sustituir una imagen mayor sobre un volumen
existente sin procedimiento de migración/restauración. La DB no publica
puerto al host. API escucha en contenedor y expone \textbf{solo
loopback} 18095; es una dirección prevista, no URL desplegada.

Flyway inicializa/actualiza esquema mediante configuración del producto.
La propuesta usa \path|sec_owner| para migración y arranque por
simplicidad del fixture; esto no acredita mínimo privilegio para
producción. Separar cuenta migradora y cuenta de ejecución y probar
permisos antes de un despliegue real. Mantener backup y ensayar
restauración coherente de DB y archivos; no se ejecutaron backup/restore
aquí.

La API usa prod, demo=false y cookie Secure=true, sin Swagger activo. Un
navegador no debe enviar esa cookie por el HTTP local previsto: para
demostrar sesión productiva se requiere TLS/proxy configurado y
verificado, o un fixture local diferente claramente separado. \textbf{No
desactivar Secure en prod para hacer pasar una demo.} No se declara TLS,
CORS ni certificados desplegados.

La imagen ejecuta como UID 10001 y raíz de contenedor de solo lectura;
\path|/tmp| y volumen de archivos son escrituras explícitas. Revisar
permisos/propietarios reales de volúmenes e imagen; no afirmar
aislamiento por copiar estas líneas. Configuración por env queda visible
a operadores del motor: evaluar secretos montados/gestor externo si el
entorno lo requiere.

\section{Validación y documentación de
API}\label{ACD5-semana-5-anexo0-validaciuxf3n-y-documentaciuxf3n-de-api}

Registrar estado de salud, logs redactados de arranque, migraciones,
digest imagen, hash JAR, versión DB y resultados del flujo protegido.
\path|pg_isready| solo indica disponibilidad de DB, no permisos ni éxito
de API. Una respuesta health 200 no demuestra funcionalidad del
incremento. Ejecutar casos VT y contrato aceptado en el aislamiento
requerido, incluidos rechazos, reinicio y persistencia.

El perfil prod deshabilita \path|/swagger-ui| y \path|/v3/api-docs| por
diseño. Publicar \textbf{documentación estática del contrato aceptado} o
un servicio de documentación separado y controlado; no habilitar
demo/Swagger productivo automáticamente. Los YAML de APE3 están
disponibles localmente; el objetivo sigue no implementado. No se publicó
documentación en un host externo.

\section{Parada, datos y
rollback}\label{ACD5-semana-5-anexo0-parada-datos-y-rollback}

Usar parada del proyecto específico; no comandos globales de limpieza ni
borrado de volúmenes. Guardar respaldo antes de cambios; seleccionar
imagen previa y plan de compatibilidad de schema. Un rollback de imagen
no revierte una migración de DB. No se proporciona un \path|down -v|
como operación rutinaria.
